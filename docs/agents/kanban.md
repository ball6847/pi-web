# Kanban board

## What it is
- A per-project task board persisted on the server at `<agentDir>/kanban/<encoded-project-root>/kanban.json` (`<agentDir>` is pi's agent directory, `$PI_CODING_AGENT_DIR` or `~/.pi/agent`): one file per project, machine-local like sessions, and shared by every browser and device that reaches the same pi-web server — and by **every worktree of the same repository**, since the key is the resolved project root. It replaces the old in-browser mock (localStorage, seeded sample cards); mock-era boards are not migrated. Before this move the board lived at `<projectRoot>/.pi/kanban.json`; that file is imported (and then deleted) on the project's first access under the new location, a corrupt one is set aside and a newer-schema one is left in place.
- Layers: `lib/kanban-types.ts` (client-safe types, `defaultLanes()`, the `KanbanAction` union, the envelope), `lib/kanban-shared.ts` (pure reducers, the board's rules, no I/O), `lib/kanban-store.ts` (server-only locked file store), `app/api/kanban/route.ts` (the one route), `lib/kanban.ts` (client cache, hooks and mutation functions the components call).
- The board view is an absolute-positioned overlay in the chat area (`AppShell`'s `centerView: "chat" | "board"`; `KanbanBoard` in an `inset: 0` layer beside the chat layer, which stays mounted under `display: none` so the session keeps its state). It is **not** a `TabBar` tab: `TabBar` is the right panel's file/terminal/subagent tabs, and the board never appears there.
- `kanban.json` is pure data: never executed, never treated as config that spawns anything, so the project-trust gate does not apply.

## File and envelope
- Path `getKanbanPath(projectRoot)` = `join(getAgentDir(), "kanban", encodeBoardKey(projectRoot), "kanban.json")`; the key is the **resolved** project root of the request's cwd (a worktree collapses to its main repository; anything else keeps its own identity — the same rule the sidebar groups sessions by, `lib/worktree.ts`), and `encodeBoardKey` wraps the resolved path as `--<path with `/`, `\` and `:` replaced by `-`>--`, the same encoding pi's session directories use (`~/.pi/agent/sessions/<encoded-cwd>/`), so a board sits beside its project's sessions and stays human-readable. `board.projectDir` is a label only (the folder the board was last read for); it no longer determines where the file lives, so a project that moves on disk keeps its board and its history. The content is `{ "schemaVersion": 1, "board": { projectDir, lanes, cards } }`. A board never written is created on the first creating read (the one write a GET makes; `?create=0` reads a missing board as empty instead) with the six default lanes (`lane-backlog` fixed, Todo, Plan, Implement, Deploy, Done) and zero cards; when the shared file is missing, the project's old `<projectRoot>/.pi/kanban.json` is imported first (or, when the main checkout has none, the newest such file one of the repository's worktrees kept), and the imported file is deleted once its content is in the shared one.
- Written atomically (temp sibling + rename, mode 0644). A file that cannot be parsed (garbage, not a regular file, over 4 MiB, bad shape) is set aside as `kanban.json.corrupt-<ms>` and a fresh board starts; the set-aside happens only on the paths that write (a creating read or a `POST`) — `?create=0` reads a corrupt file as an empty board with revision `0` and never touches it, and never imports a legacy file either. A file with `schemaVersion > 1` is **refused** (`unsupported-schema`, 500) and left untouched — including a legacy file that is refused for that reason, which stays where it is and is not imported.
- The board is per project, so keeping it out of version control is a one-line choice in the project's own `.gitignore`: `.pi/kanban.json` (use `.pi/kanban.json*` to also cover the corrupt-backup siblings). Without the line the board is tracked like any other file; the write path does not force either way.
- Hand edits are read leniently: invalid cards are skipped, a card in a vanished lane goes to the backlog (unlinked), a session carried by two cards stays on the first, and `projectDir` is always overwritten with the folder read.

## Route (`app/api/kanban/route.ts`)
- `GET ?cwd=<project folder>` → `{ board, revision }`. `GET ?cwd=&revOnly=1` → `{ revision }`, a pure stat: no parse, no write, no pruning (`0` while no board exists). The revision is a float — compare with `!==`, never as an integer.
- `POST { cwd, action, ...payload }` → `{ board, revision }`. Actions: `add-card`, `edit-card`, `delete-card`, `move-card`, `advance-card`, `link-session`, `unlink-session`, `create-card-for-session`, `add-lane`, `rename-lane`, `move-lane`, `delete-lane`. `add-card` / `create-card-for-session` / `add-lane` accept a client-chosen `cardId` / `laneId` so an optimistic card and the server's card share an id (a duplicate id is refused).
- The folder is validated first, exactly as `/api/mcp` validates its project (`validateMcpProject`). Failures are typed `{ error, code }`, never a stack: 400 `cwd-invalid` / `cwd-not-directory` / `invalid-request` / `refused` (a board rule), 403 `cwd-denied` (also for a folder that does not exist: the allowed-roots check comes first), 404 `session-missing`, 415 wrong content type, 423 `locked`, 500 `internal` / `unsupported-schema`. Nothing is written on a refusal.
- **`session-missing` is transient.** pi writes a session's file only after its first message, so `link-session`, `create-card-for-session` and an `add-card` that carries a `sessionId` can 404 for a moment after the session got its id. The client re-posts such a write a few times (1.5 s apart) and only then rolls back, shows the banner and keeps the write for **Retry**. Never treat it as permanent.

## Store, lock and revision (`lib/kanban-store.ts`)
- Every write is read → reducer → validate → write under an in-process queue (`serializeByKey`, one chain per board file) plus a `proper-lockfile` lock, as `lib/session-ui-state.ts` does. The lock waits through 10 exponential retries (25 ms doubling to a 500 ms cap, a ≈ 3.3 s budget) and answers 423 when that budget runs out — a second pi-web process racing the same board is the case that hits it (the in-process queue already serializes one process's own writes). A lock held for more than 10 s is treated as stale and taken over, so a crashed server never pins a board. Store functions return typed results (`{ ok, board, revision } | { ok: false, code, error }`) — nothing throws at the route.
- Revision = `max(in-process write counter, file mtimeMs)`; the counter moves strictly forward on each write (even two writes in one mtime tick), the mtime part makes an edit from another process or another pi-web server visible.
- A mutation that changes nothing (the reducer returns the **same board object**) writes nothing — and therefore leaves the revision standing, so the poll sees no change.
- The one write a refused mutation can make: when the edit finds no board, the fresh one is written (with the counter noted) even though the action itself is refused, so the next read sees a real board with a real revision.

## Pruning (dead sessions)
- On every board read and inside every mutation (same lock), a card whose `sessionId` no longer has a session file is unlinked: it keeps its lane and its snapshot `sessionTitle`. A read writes only when something was actually dead. Existence is the cached session path re-verified with `existsSync`; a stale path cache is invalidated and re-resolved (a dead session costs one directory scan, once — the link is gone afterwards).
- A session belongs to a board when its header `cwd` equals the board folder **or** `resolveProject(header.cwd).projectRoot` does. The client keys boards by `session.projectRoot ?? session.cwd`, so worktree sessions count against the project root.
- A session's existence for `link-session` / `create-card-for-session` / `add-card` is checked in the store (`applyMutation`) before any lock or mkdir.

## Board rules (`lib/kanban-shared.ts`)
- Reducers return a new board, the same object for "nothing changed", and `null` for "refused"; callers pass `now`.
- The first lane is the fixed backlog (`lane-backlog`, `fixed: true`): its cards carry a title and a description only, never a session. It cannot be renamed, moved or deleted, no lane swaps past it, `ConfigLaneRow` draws it with a padlock, the card form has no session picker there, and the composer's lane menu disables it ("The backlog never takes a session").
- A sessionless card only rests in the backlog: `moveCardToLane` refuses a sessionless card going to a work lane. `advanceCard` is not guarded that way (a backlog card still advances one lane). **A card with a session cannot be moved into the backlog** (`null`).
- **`deleteLane` relocates the lane's cards to the backlog** — unlinked, with the snapshot title kept (the backlog holds no session). The old mock refused to delete a lane with cards; the lane config dialog still disables Remove while a lane holds cards (`kanban.configureRemoveBlocked`), so the UI never asks for the relocation, but the API does it.
- **Unlinking keeps `sessionTitle`** (only `sessionId` clears), including the old card when linking a session that was on another card.
- One session, one card: `linkCard` / `addCard` drop the link off any other card carrying the session; `createCardForSession` reuses the existing card (only the title refreshes) and otherwise adds one in the composer's lane, falling back to the first work lane.
- Lanes after the backlog are user-configurable: add, rename (Enter or blur saves), reorder, delete (`LaneConfig` + `ConfigLaneRow` in `components/KanbanBoard.tsx`).
- The user moves a card with `move-card` — a drag, or the card menu's "Move to {lane}" entries: the card lands last in the target lane (the board has no card order of its own) and the same rules gate it (`moveCardToLane`). Advancement is a demo action standing in for the model's decision: "Demo: advance to {lane}" (`kanban.menuAdvance`) on the card menu and the strip menu calls `advance-card`, one lane right. Linking a session does **not** move its card.
- Each project directory has its own board (`kanbanContextDir`: the session's `projectRoot ?? cwd`, for a fresh composer its context project's root). The link picker and "Open session" see the project's top-level sessions only (`boardSessions` filters out `relation.kind === "subagent"`).

## Client cache (`lib/kanban.ts`)
- A module-level `Map` of entries keyed by project root. An entry holds the last `serverBoard`, its `revision`, the `pending` writes and the shown `board` = server board with pending writes folded on top (the `useSessionUiState` pattern). `useKanbanBoard(dir)` returns that board or `null` while loading; `useKanbanBoardStatus(dir)` returns `{ status: "loading" | "ready" | "error", error?, retry() }`. The banner's `retry()` does three things: it re-enqueues the writes the entry kept as `retryable` (the session-missing failures from the section above — re-posted, not dropped), clears the error, and refetches with the entry's normal read kind — a creating read only while a board-view (creating) watcher holds the board, so a board whose initial creating read failed is created now; a strip-only board refetches non-creating, as its quiet resyncs do).
- Mutation functions keep the mock's names and **synchronous** return values (`kanbanAddCard` → `KanbanCard | null`, `kanbanAdvanceCard` → `KanbanLane | null`, the rest `void`). Each runs `applyKanbanAction` from `kanban-shared` first: a `null` refusal never posts and changes nothing; a same-board result does not post either. Otherwise it is applied optimistically and POSTed, writes of one board go out one at a time. On success the server's `{ board, revision }` replaces the cache (and a GET that began before it is discarded via `loadId`); on failure the pending write is dropped (rollback), the status turns `error` and a quiet refetch resyncs. Without a loaded board, mutations are no-ops except `kanbanCreateCardForSession`, which posts blind (the server holds the rules). `kanbanBoardSnapshot(projectDir)` reads the shown board outside a render — the pending attach's consume-time lookup — and `kanbanBoardSnapshotForTests` delegates to it.
- Polling: watching a board (`useKanbanBoard` / `useKanbanBoardStatus`) fetches it on mount, then `GET ?cwd=&revOnly=1` every 2.5 s (the running-sessions cadence in `SessionSidebar`) while the tab is visible — skipped while hidden, one check as soon as it is shown again — and a moved revision refetches the whole board. One in-flight fetch per board; the poll does nothing while a write is pending. A board with no watcher is not polled.
- `useKanbanSessionIndex()` derives `Map<sessionId, KanbanSessionInfo>` from the boards **loaded in this tab** (the current project's, plus any other the user opened); the sidebar's tracked marker therefore shows for the watched project's sessions, not every project's.

## Surfaces
- **Chat-top lane strip** (`components/KanbanLaneStrip.tsx`, `ChatWindow`'s `kanbanStrip` prop, first child of `.chat-content`): the project's lanes left to right as pills, only the card's lane highlighted (a dot on it while the session runs), the card title at the left. It renders nothing until the board has loaded (a strip flash is worse than momentary absence) and has no status UI. The menu offers View board, the Demo advance (same gating as the card menu: only while a next lane exists, dimmed) and Unlink; an untracked session gets "New card in {lane}" plus "Attach to" the board's sessionless cards, newest first and uncapped (the menu's own filter, shown past six entries, finds the rest). The pill states: only the current lane takes the accent tint and the running dot; past lanes a plain hover tone, the rest 55% opacity; the pending pill is dashed. The label at the left is the card's title when tracked, "Not on board" for an untracked session, and the pending text for a fresh composer; a fresh composer with no pending lane renders no strip at all (`isNewSession && !card && !showPending` → null). A fresh composer shows its pending choice as a dashed pill on the lane it will touch — a new card's lane, or the attached card's current lane — labeled "New session — starts in {lane}" or "New session — starts on card {title}"; the pill highlights only while the lane resolves (a card deleted on another device leaves the label alone).
- **New-session composer** (`components/NewSessionContextBar.tsx`): the "Track on board" choice (the `board` prop, `data-kanban-board-choice` menu) is three-way — Off, "New card in" a lane (backlog disabled, tooltip says why), or "Attach to card" one of the board's sessionless cards — newest first (`sessionlessCardsByRecency`), uncapped, each row tagged with its lane; past six cards a filter field narrows the list by title (the card menu's filter pattern, `kanban.composerCardFilter`), with a disabled "no match" line when the filter empties it and a disabled "no cards" line when the board has none. The pick (`KanbanNewSessionPick`, `lib/kanban-types.ts`) is AppShell state (`newSessionKanbanPending`, pinned to `composerBoardDir` by `handleNewSessionKanbanPick`), owned by the parent, not the bar. It is per composer: the reset effect runs on every `composerBoardDir` change and keeps a choice only for the same board (a worktree move keeps it — the board belongs to the project root), and `handleSessionCreated` clears it (state + ref) after applying it, guarded by the draft key: a new-card pick calls `kanbanCreateCardForSession`, an attach pick looks the card up in `kanbanBoardSnapshot` at that moment — a backlog card is advanced one lane first (`kanbanAdvanceCard`, the store refuses the link there), then `kanbanLinkCard`; a card that meanwhile got linked or deleted is refused and the choice is dropped quietly. Its lane and card lists are empty until the board loads (`contextBoard`).
- **Sidebar** (`components/SessionTree.tsx`, via `SessionSidebar`'s `kanban` prop): a tracked session row shows the small board glyph (`session-tree-kanban`, "On board · {lane}") for the family root id from `useKanbanSessionIndex()`, which AppShell calls and passes down (the tree only reads it), so subagent rows show the parent's marker. A project group header gets the board icon ("Open {name}'s board") whenever the `kanban` prop exists — it does, for every group — that opens that project's board (`openKanbanBoardView`, which also rings the jumped-to card for 2.4 s when a card id is passed).
- **The board itself** (`components/KanbanBoard.tsx`): lane columns, a card form and the card menu (`CardMenu`), the link picker (`SessionPicker`), and the lane config dialog over the columns. A card is also draggable to another lane: `hooks/useKanbanCardDrag.ts` runs the same pointer state machine as the sidebar's group drag (mouse arms after 4 px, touch/pen after a 350 ms held press with 8 px slop, second-finger and Escape cancel, auto-scroll at the edges), but hit-tests the lanes by rect (`data-kanban-lane` / `data-kanban-lane-cards`) instead of drop targets, auto-scrolls the row horizontally plus the hovered lane's card list vertically, and floats a ghost over the board while the source card dims; releasing posts `move-card`. From pick-up, every lane the move-card rules refuse for the card in flight shows itself undroppable — dashed red border, red wash, `no-drop` cursor, and a one-line reason in the lane header (the source lane excepted) — and a release on one bounces back with no write. In the phone's one-lane view the same held press opens the card menu instead (the menu's outside-close ignores that press's synthetic mousedown for a short window), so "Move to" is the phone's — and the keyboard's — move path. The card menu's entries are gated by link state: a linked card gets Open session (disabled with "That session is no longer available" when the session is gone) and Unlink; an unlinked one gets Start session (always enabled; `onStartSession` hands the card to AppShell's `handleKanbanStartSession`, which opens the fresh composer for the board's project with the card's title and description as the starting draft — parked under the cwd's draft key so `handleNewSession` picks it up — pins the pending attach choice and switches to the chat view; the session is linked when it is created, nothing is written before) and Link (disabled for a backlog card or a project with no sessions, opening the picker otherwise); Edit is always there, and "Move to {lane}" covers every other lane (disabled where the rules refuse it, with the reason as the hover text); the dimmed "Demo: advance" appears only while a next lane exists; Delete is last, marked danger. The config dialog's rows: rename saves on Enter (via blur) or blur, up/down are barred for the fixed backlog and at the edges, and Remove is enabled only for a lane with no cards (`kanban.configureRemoveBlocked`). While the board loads the lanes' area holds a slim placeholder (`kanban.loadingBoard`) inside the same frame (`BoardShell`), so the columns arrive without a layout jump; a failed load or write shows a one-line banner with Retry (`kanban.loadFailed` / `kanban.retry`, `BoardNotice`) above the lanes (the rolled-back board stays visible). The top-bar Chat/Board toggle (`renderBoardViewToggle` in `AppShell`) switches `centerView` (the Chat button forces `chat`, picking any session in the sidebar does too — "the user wants its chat, not whatever the center shows"); it hides when no chat context exists but stays up while the board view is on, so the way back always shows. `AppShell` keeps two watchers: `contextBoard` — the strip's project (the selected session's `projectRoot ?? cwd`, or the fresh composer's context project) — is watched whenever that context exists (the strip, the sidebar's board highlight and the composer's lane list all read it), while `viewBoard` is watched only while `centerView === "board"`. When both name the same project (the common case) they share one refcounted entry, so the current project keeps polling in the chat view; another project's board polls only while it is on screen. Switching back from chat re-acquires `viewBoard`, which checks the revision immediately (acquire's cached-board path) rather than waiting for the next tick. A move (drag, "Move to" or demo advance) rings the moved card for 1.6 s, and arriving with a highlighted card opens its lane in the mobile one-lane-at-a-time view.
- **The link picker** (`SessionPicker` in the same file): a portal `listbox` anchored to its trigger (clamped 8 px from the edges, flips above when the bottom edge is close). It lists the project's whole top-level session list — **no cap**; the filter field (case-insensitive title substring) is the finder — with each row's title `name || firstMessage || id` and a running flag. Escape (capture, so it never reaches the board's Escape handling) or a mousedown outside the picker closes it. Two consumers pick differently: the card form's picker sets the form's session field (the form shows `kanban.cardFormSessionRequired` when the project has no sessions), while the card menu's Link picker calls `kanbanLinkCard` directly on pick.
- Every label lives in the `kanban.*` keys of `lib/i18n/messages/en.ts` (and zh-CN, zh-TW); `kanban.configureNote` is the one paragraph that states the board's rules in the config dialog.
- **A card's activity indicator** (the linked-session chip's leading slot — a fixed-width slot that holds the session glyph when idle and the state while the session is active, so a state flip shifts nothing and can never overflow the card): the sidebar row's states, precedence and labels — the amber `session-tree-awaiting` dot (`sidebar.agentAwaitingInput`) while the linked session is parked on an extension's dialog, else the running spinner (`SpinnerIcon`, `sidebar.agentRunning`), else the blue `session-tree-unread` dot (`sidebar.newSessionActivity` / `sidebar.newActivity`) for new activity this browser has not opened. It reads `runningSessionIds` / `awaitingInputSessionIds` / `unreadSessionIds`, the sets `SessionSidebar` already keeps and reports up to `AppShell` (`onRunningSessionIdsChange`, `onAwaitingInputSessionIdsChange`, `onUnreadSessionIdsChange`); the board fetches nothing of its own. `CardView` is exported for `components/KanbanBoard.card-activity.test.mjs`, which pins the states, the precedence and the shared labels.

## Traps
- `useSyncExternalStore`'s `getServerSnapshot` must return a **stable cached reference** (`null` / the shared `LOADING_VIEW` / `0` here); a fresh object per call triggers "The result of getServerSnapshot should be cached to avoid an infinite loop" and re-renders forever. The status hook's `{ status, error }` view is cached on the entry and only rebuilt when it changes for the same reason.
- `useKanbanSessionIndex()` mutates its module-level `lastIndex` map in place (drops stale keys, rewrites only changed entries) and returns that one map. Unchanged `KanbanSessionInfo` entries keep their identity, so a board change re-renders only the rows whose marker actually moved; a rebuilt map would re-render every session row.
- Board objects are immutable. An identical refetch keeps the old object (`adopt` compares JSON), so memoizing on the board is safe and a poll tick does not re-render.
- Only a creating read (a `GET` without `?create=0`, the board view's) creates the shared board file for a project that has none (importing its legacy `<projectRoot>/.pi/kanban.json` first, when it holds a board); the strip and composer watchers send `create=0` and read a missing board as empty (revision 0), so merely selecting a session writes nothing anywhere. Do not add a creating watcher speculatively (e.g. for every sidebar project).
- The "Demo:" prefix on the advance action (`kanban.menuAdvance`) marks the model's decision the user runs on its behalf — one lane right, what the model will post on its own — while the plain "Move to" entries are the user's manual `move-card` moves, to any lane the rules allow. Keep that distinction.

## Not built
- The model advancing cards on the protocol side: the card moves when the model decides the stage is done, replacing the "Demo:" menu entries.
- A push channel for the board (the revision poll is the sync) and undo; several boards per project.

# Kanban board

## What it is
- A per-project task board persisted on the server in **SQLite** at `<agentDir>/kanban/<encoded-project-root>/kanban.sqlite` (`<agentDir>` is pi's agent directory, `$PI_CODING_AGENT_DIR` or `~/.pi/agent`): one file per project, machine-local like sessions, and shared by every browser and device that reaches the same pi-web server — and by **every worktree of the same repository**, since the key is the resolved project root. It replaces the old in-browser mock (localStorage, seeded sample cards); mock-era boards are not migrated.
- Storage history, newest first: SQLite (now) ← `kanban.json` beside the database ← `<projectRoot>/.pi/kanban.json`. Both JSON generations are imported on the project's first access and then **kept as `.imported-<ms>`** (never deleted: a bad import must stay recoverable); a corrupt one is set aside as `.corrupt-<ms>`, and a newer-schema one is left exactly in place.
- Layers: `lib/kanban-types.ts` (client-safe types, `defaultLanes()`, the `KanbanAction` union, the envelope), `lib/kanban-shared.ts` (pure reducers, the board's rules, no I/O), `lib/kanban-data.ts` (server-only SQLite: schema, rows, revision — the **only** place SQL exists), `lib/kanban-store.ts` (server-only policy over it: lock, seeding, pruning, typed refusals), `app/api/kanban/route.ts` (the one route), `lib/kanban.ts` (client cache, hooks and mutation functions the components call).
- The board view is an absolute-positioned overlay in the chat area (`AppShell`'s `centerView: "chat" | "board"`; `KanbanBoard` in an `inset: 0` layer beside the chat layer, which stays mounted under `display: none` so the session keeps its state). **Esc on the board is the board's.** Because the chat layer stays mounted, ChatWindow's registered abort handler would answer an Esc pressed on the board and stop the session running behind it (also taking the key from the board's own Escape handling). `useGlobalKeyboardShortcuts` therefore takes `escapeStopsAgent`, and `AppShell` passes `centerView === "chat"`: on the board the window-level Esc shortcut is inert, so a card or lane drag cancels, a menu closes, and the run keeps going. Back on the chat it is armed again. It is **not** a `TabBar` tab: `TabBar` is the right panel's file/terminal/subagent tabs, and the board never appears there.
- **The board screen is in the URL, as `?board=<projectDir>`.** `getInitialNavigation()` reads it back as `boardProjectDir`, `AppShell` seeds both `centerView` and `boardProjectDir` from it, and an effect on those two writes it with `history.replaceState` (`boardViewUrl()` / `withoutBoardView()` in `lib/initial-navigation.ts`). It sits **beside** the chat context (`?session=`, `?cwd=`, `sidebar`), so the page under the board is untouched and Chat is one parameter away. `history.replaceState`, not `router.replace`: only mount reads this URL, and a Next replace remounts through Suspense (the trap `handleSelectSession` documents). Without it a reload dropped `centerView` to its `"chat"` default and the board was gone. A **restore is not a pick**: `handleSelectSession(session, true)`, the sidebar replaying the URL's or this tab's session on mount, must not force `chat`, or every reload of a board would land on the chat. A real pick (no `isRestore`) forces the chat, and so does the fresh composer: `handleNewSession` sets `centerView` to `"chat"`, or New (sidebar, `Ctrl+Alt+N`, the bar's move) with the board up left the user staring at the same board — the same switch `handleKanbanStartSession` makes for a card's "Start session". `handleCwdChange`'s bare-path reset still does not force it, so a cwd move leaves the board view up.
- `kanban.sqlite` and the JSON boards it imports are pure data: never executed, never treated as config that spawns anything, so the project-trust gate does not apply.

## File, schema and revision
- Path `kanbanBoardPath(projectRoot)` = `join(kanbanBoardDir(projectRoot), "kanban.sqlite")` where the directory is `join(getAgentDir(), "kanban", encodeKanbanProjectKey(projectRoot))`; the key is the **resolved** project root of the request's cwd (a worktree collapses to its main repository; anything else keeps its own identity — the same rule the sidebar groups sessions by, `lib/worktree.ts`), and `encodeKanbanProjectKey` wraps the resolved path as `--<path with `/`, `\` and `:` replaced by `-`>--`, the same encoding pi's session directories use, so a board sits beside its project's sessions and stays human-readable. `board.projectDir` is a label only (the folder the board was last read for); it is never stored in a row, so a project that moves on disk keeps its board and its history.
- The schema (`lib/kanban-data.ts`, `SCHEMA`) is five `STRICT` tables: `meta(key, value)` (the `revision` counter, and the card-key state: `card_prefix`, `next_card_number` and, only after a rename, `card_prefix_aliases` as a JSON array), `lanes(id, position, name, description, instructions, fixed)`, `cards(id, position, lane_id, number, title, description, session_id, session_title, created_at, updated_at)`, `card_comments(id, card_id, author, session_id, session_title, body, created_at)` and `card_activity(id, card_id, kind, from_value, to_value, actor_session_id, actor_session_title, created_at)`, plus a unique index on `cards(session_id) WHERE session_id IS NOT NULL` — "one session, one card" is now enforced by the file too — and `cards(number) WHERE number > 0`, the card key's number (`0` is the repair bucket a hand-edited row carries until the reader numbers it). `PRAGMA user_version` is the schema stamp (`KANBAN_SCHEMA_VERSION`, currently 5). **Neither `card_comments` nor `card_activity` has a foreign key to `cards`**: `writeBoardRows` replaces the card rows wholesale on every board write, and an `ON DELETE CASCADE` would take every thread and every history row with it on an unrelated edit. The writer prunes the rows whose card is gone (one `DELETE ... WHERE card_id NOT IN (SELECT id FROM cards)` per table) in the same transaction, so a deleted card's thread and trail go with it and nothing else does. `lanes.instructions` is the model-facing "how to work here" text injected when a card enters the lane; `description` stays pure UI text and is never injected.
- `GET ?cwd=&cardId=` on **`app/api/kanban/activity/route.ts`** is the same read for a card's derived history (`{ cardId, activity, total, revision }`, `&before=<id>` pages backwards); see "Card activity".
- `GET ?cwd=&cardId=` on **`app/api/kanban/comments/route.ts`** → `{ cardId, comments, total, revision }`: one card's thread, oldest first, the newest `KANBAN_COMMENT_PAGE_LIMIT` (100) rows with `total` counting them all. Never creating (a missing board answers empty at revision 0) and never pruning; it takes the same request gate as the board view's creating read because an older file may be migrated on open.
- **A board's order is its rows' `position`** (`ORDER BY position`), for lanes and cards alike. The tables are independent (a card moves between lanes), so positions are 0-based and dense per table, rewritten on every write.
- The file's state is `ready` (this schema), `migrate` (an older schema this build upgrades), `missing` (nothing is created by looking), `empty` (a valid SQLite file with no board schema — what an interrupted first open leaves), `corrupt` (not a database: garbage, truncation) or `newer` (a `user_version` above this build's). A `corrupt` or `empty` file is replaced by a fresh board on a writing path; a `newer` one is **refused** (`unsupported-schema`, 500) and left untouched.
- **Schema upgrades are in-place migrations** (`migrateKanbanDatabase`, the `MIGRATIONS` map): any open of an older file — a reading open included, because the rows cannot be read without the columns — applies the additive, lossless steps from its stamp up and stamps the new version inside one transaction (`BEGIN IMMEDIATE`, so two concurrent openers cannot both run a step). v1→v2 adds `lanes.instructions TEXT NOT NULL DEFAULT ''`; v2→v3 creates `card_comments` and its `(card_id, created_at)` index; v3→v4 creates `card_activity` and its `card_id` index (both new tables, so no existing row changes); **v4→v5 adds `cards.number`**, numbers the existing cards in creation order (`ROW_NUMBER() OVER (ORDER BY created_at, id)`), builds `cards_number` and starts `meta.next_card_number` after the highest. One version belongs to one step, so the number step is keyed at 4: a board that already crossed to v4 keeps its rows and gains the column here instead of failing on a duplicate column. **A migration never bumps `meta.revision` — except into v5**, which gives every card a number the views now show: a cached client must refetch for its card keys, and the moved revision is how it is told. That is the one step whose result is content, not storage. This is the one write a reading open of an *old* file makes; missing files are still never created by looking. `getBoardRevision` (the poll) stays a pure `meta` read that answers an old file's revision without migrating it. A failed migration rolls back, leaving the file at its old version (a later writing path then sets it aside as corrupt, as before).
- Written wholesale inside one `BEGIN IMMEDIATE` transaction (`writeBoardRows`), which also bumps `meta.revision` — a board is dozens of rows, so one statement per table beats a diff. The connection is opened, used and closed inside the lock, so a closed board is a single file (the default rollback journal leaves no `-wal`/`-shm` sidecars).
- **The revision lives in the file** (`meta.revision`), not in process memory: any reader — this process, another one, another pi-web — sees the same number, the client's 2.5 s poll only refetches when a write actually landed, and no `globalThis` counter can drift. A mutation that changes nothing (the reducer returns the **same board object**) writes nothing and therefore leaves the revision standing.
- Hand edits are read leniently by the row reader: a card whose lane is gone goes to the backlog unlinked, a duplicate session beyond the first card is dropped, and `projectDir` is always the folder the board was read for.
- A board never written is created on the first creating read (the one write a GET makes; `?create=0` reads a missing board as empty instead) with the six default lanes (`lane-backlog` fixed, Todo, Plan, Implement, Deploy, Done) and zero cards.

## Migration of the replaced JSON boards (`seedBoard` in `lib/kanban-store.ts`)
- A missing database is seeded, newest storage first: (1) `kanban.json` beside the database — the storage SQLite replaced, (2) the project's own `<projectRoot>/.pi/kanban.json` — the location before that, (3) the **newest** such file one of the repository's worktrees kept (only the newest, so a stale copy never shadows a fresher board; this is how a board that forked in a worktree before the earlier move is recovered), then (4) the default board. A `0`-byte database (an interrupted first open) takes the same path: it holds no board to keep.
- The imported file is **kept** as `kanban.json.imported-<ms>` beside the database, never deleted. A superseded copy (an older JSON board the import made redundant) becomes `.superseded-<ms>`, so it cannot be imported later if the database ever goes missing. A corrupt one becomes `.corrupt-<ms>`.
- A JSON board from a **newer** schema is left exactly where it is and the search stops: importing it is impossible, and any copy elsewhere is staler than a file this build cannot read. The JSON generation is frozen at `KANBAN_JSON_SCHEMA_VERSION` (1 — the last version that storage wrote), so "newer" for a JSON file means above 1, whatever the database's own stamp is; a newer-schema *database* is the `unsupported-schema` refusal instead.
- The import reads the old envelope through `parseJsonBoard()`, still lenient exactly as that storage read it: invalid cards skipped, a card in a vanished lane to the backlog unlinked, a session carried twice kept on its first card.

## Route (`app/api/kanban/route.ts`)
- `GET ?cwd=<project folder>` → `{ board, revision }`. `GET ?cwd=&revOnly=1` → `{ revision }`, a pure read: one `meta` row, no board parsing, no write, no pruning (`0` while no board exists). The revision is a whole number that only ever moves forward — compare with `!==`.
- `POST { cwd, action, ...payload }` → `{ board, revision }`. Actions: `add-card`, `edit-card`, `delete-card`, `move-card`, `advance-card`, `link-session`, `unlink-session`, `create-card-for-session`, `add-lane`, `rename-lane`, `edit-lane`, `move-lane`, `reorder-lane`, `delete-lane`, `set-card-prefix { prefix }`, and the two comment writes `add-comment { cardId, body }` / `delete-comment { commentId }` (see "Card comments"). `add-card` / `create-card-for-session` / `add-lane` accept a client-chosen `cardId` / `laneId` so an optimistic card and the server's card share an id (a duplicate id is refused). `move-card` takes `{ cardId, laneId, beforeCardId? }`: `beforeCardId` places the card right before that card of the target lane, null or absent puts it last (the route's `optional()` keeps a non-string a 400 `invalid-request`).
- The folder is validated first, exactly as `/api/mcp` validates its project (`validateMcpProject`). Failures are typed `{ error, code }`, never a stack: 400 `cwd-invalid` / `cwd-not-directory` / `invalid-request` / `refused` (a board rule), 403 `cwd-denied` (also for a folder that does not exist: the allowed-roots check comes first), 404 `session-missing`, 415 wrong content type, 423 `locked`, 500 `internal` / `unsupported-schema`. Nothing is written on a refusal.
- **`session-missing` is transient.** pi writes a session's file only after its first message, so `link-session`, `create-card-for-session` and an `add-card` that carries a `sessionId` can 404 for a moment after the session got its id. The client re-posts such a write a few times (1.5 s apart) and only then rolls back, shows the banner and keeps the write for **Retry**. Never treat it as permanent.

## Card keys (`PIW-42`)

- A card has a **human handle beside its storage id**: `number` (an integer, assigned once at creation, monotonic per board, never reused after a delete) rendered through the board's prefix — `PIW-42`. **The prefix is never stored on a card and the key is never stored anywhere**: `meta.card_prefix` + `cards.number` are the truth, and every view composes them (`kanbanCardKey()` in `lib/kanban-types.ts`). That is what makes a rename one meta write instead of a rewrite of every card row.
- **The prefix is per board**, i.e. per resolved project root, exactly like the board itself: every worktree, every browser and every device sharing this pi-web sees the same one, and the agent tool renders the same key the user reads. It is *not* repo config: the board is machine-local storage, so a git-tracked prefix would let two clones disagree about what `PIW-42` names.
- **A new board derives its prefix from its folder** (`defaultCardPrefix`: the last path segment's letters and digits, uppercased, first five — `pi-web` → `PIWEB`; a name with no usable letters → `CARD`). It is only a default; the user renames it.
- **Prefixes are unique among the boards of one machine** (`takenCardPrefixes()` in `lib/kanban-store.ts` scans `<agentDir>/kanban/*/kanban.sqlite` for stored `card_prefix` rows). A derived default that collides gets a suffix (`PIWEB2`); an explicit save that collides is **refused** (`refused`, "already belongs to another project's board"). Two projects answering to `PIW-42` would make every reference — a commit message, a branch name, a prompt — ambiguous, which is the whole point of the feature. Only stored prefixes count: a board that never wrote one has no cards, and picks a free one before its first write (`editBoard`'s `needsPrefix`, which is also how a v3 file migrated in place or an imported JSON board gets one).
- **Renaming keeps the old prefixes as aliases** (last 5, `meta.card_prefix_aliases`, newest first). `setCardPrefix()` (`lib/kanban-shared.ts`) renames atomically — every card reads `WEB-12` at once — and an alias list keeps `PIW-12` resolving, so a reference written yesterday still lands. The Confirm-free Configure field is the whole UI: there is nothing to migrate and nothing to renumber.
- **Numbers are allocated by the shared reducer**, not the store: `addCard` takes `board.nextCardNumber` and bumps it, so the optimistic client shows the real key before the answer, and folding pending writes over the server board (`applyKanbanAction`) stays pure and deterministic. `nextCardNumber` is persisted in `meta` and only ever grows; a deleted card's number is retired for good. A same-lane no-op writes nothing, so the counter cannot run away. A concurrent create from another tab can make the optimistic number stale for one round trip; the server's board replaces it.
- **References resolve through one function**, `resolveKanbanCardRef(board, ref)`: the storage id, the key (`PIW-42`, case-insensitive, current prefix or any alias) or — within one board — the bare number (`42`). A key of a *foreign* prefix resolves to nothing, so a stray `OTHER-1` never silently means this board's card 1. It is applied where the id was taken: `resolveKanbanActionRefs` for browser mutations (`move-card`'s `beforeCardId` included), `resolveKanbanToolCard` and the one-card read for the agent tool, and `add-comment`'s target. Client-chosen ids on `add-card` / `create-card-for-session` are deliberately left alone (they name a card that does not exist yet).
- **Surfaces**: the board card's own chip above its title (mono, dim, filter-highlighted), the card menu's "Copy key {key}", the detail tab's key chip, the chat lane strip's `PIW-42 · title`, and the agent tool. **The two chips are the copy button** (`components/KanbanCardKeyChip.tsx`, one control in two sizes): a click writes the key to the clipboard and confirms it — the chip turns accent and gains a check for `KANBAN_CARD_KEY_COPIED_MS`, while a `role="status"` line says "Copied"; a refused write says "Copy failed" instead of claiming one. It stops both `click` (the card would open its detail tab) and `pointerdown` (the card would start a drag), so a press on the key is never also a press on the card. The tool's overview carries `cardPrefix`, every card projection carries `number` and `key`, and a search row carries `key` — so a model can speak the same reference a person does. The board's own filter matches the key too (`cardMatchesQuery(card, query, key)`), so typing the reference into Filter cards finds the card.
- **The board notice speaks the key** (`Kanban: this session is on card PIW-42.`) because that is what the user and the model both recognize; the dedupe signature stays the card *id*, so a prefix rename (which changes no link and no lane) announces nothing and the next `kanban read` shows the new key.

## Agent tool (`kanban`)

- `lib/kanban-extension.ts` exports `createKanbanExtension(options?: { isReadOnly?: (ctx: ExtensionContext) => boolean }): InlineExtension`. It registers one ordinary Pi `direct` tool, with flat TypeBox parameters and no board injection into the system prompt. Runtime callers omit the extension for Chat-only sessions; children supply their profile/snapshot read-only callback rather than using a normal-session pin.
- **Reads are projections, never the whole board.** A big project holds hundreds of cards with multi-paragraph descriptions; returning every body costs tens of thousands of tokens on a call the model makes just to find out what exists. So `read` has three shapes, and only one of them ever sends a card body:
  - `read {}` → `{ ok, action, projectDir, lanes: [{ id, name, description, fixed?, cardCount }], totalCards, currentCard, revision }`: the lanes in board order with their counts, the board total, and **this session's own card in full** (`null` when it has none). No other card is in the payload, whatever the board size, and no lane instructions either — those are injected when the card enters a lane, not listed on every read (`kanbanToolOverview` projects the lanes explicitly, never `...lane`). This is the entry point: it answers "what lanes exist, how much is where, what am I on" for a few hundred tokens.
  - `read { cardId }` → `{ ok, action, projectDir, card: <full card>, lane, nextLaneId, currentCardId, revision, comments, commentCount, activity, activityTotal }`: exactly one card, description untruncated, the lane it sits in and the next lane (`null` at the last), plus the newest `KANBAN_COMMENT_READ_LIMIT` (10) comments with bodies bounded at `KANBAN_COMMENT_BUDGET` (800) code points, `commentCount` for the whole thread, and the newest `KANBAN_ACTIVITY_READ_LIMIT` (5) activity lines (`{ kind, at, from?, to?, actor? }`, ~20 tokens each) with `activityTotal` — the same shape a mutation answers with, plus the handoff and the history. An unknown card (or a card whose lane vanished) is a `refused` error pointing back at `read`/`search`, never an empty success.
  - `search { query?, laneId?, limit? }` → `{ ok, action, projectDir, lanes: [{ id, name, cardCount }], cards: [{ id, title, laneId, linked?, excerpt }], matched, total, hasMore, hint?, currentCardId, revision }`: literal text (title **or** description, the board view's own matcher) and/or one lane, in board order. A row carries an id, the title, the lane, `linked: true` when a session owns it, and a **one-line excerpt** of the description — whitespace flattened, the first query hit centered, `…` only at the cuts, `KANBAN_CARD_EXCERPT_BUDGET` (120) code points. `matched` counts every hit and `hasMore` plus a `hint` say what was cut, so the model narrows the query instead of paging the board; `limit` defaults to 20 and cannot exceed 50 (`KANBAN_SEARCH_DEFAULT_LIMIT` / `KANBAN_SEARCH_MAX_LIMIT`, `lib/kanban-tool-limits.ts`). An unknown `laneId` is `refused` with the lane-list hint.
  - All three use `readBoard({ create: false })`: no mkdir, initialization, import, repair, pruning or revision change. A missing board has the default lanes and revision 0. `search` with no query is the "browse, cheapest possible" call: 20 compact rows and the counts, not the board.
- **The board notice** (`KANBAN_CARD_NOTICE_TYPE` = `pi-web:kanban-card`): two facts the model cannot see otherwise — which card this session is linked to, and which lanes the board has — handed over by a `before_agent_start` handler as one `display: false` custom message. `display: false` keeps it out of the chat (`isHiddenCustomMessage`); it is context for the model only. **It carries state transitions, nothing else**: no card title, no description, no lane names or descriptions, no counts, no instructions (the tool description has those, `kanban read` has the detail).
  - The state is three halves (`details: { card, lanes, laneInstr }`): the card half is the **linked card's id or `none`**; the lane half is the **lane ids in board order** (`kanbanLaneSignature`); the lane-instructions half is the **card's lane id plus a FNV-1a hash of its instructions** (`kanbanLaneInstructionSignature`, `none` when the card has no lane or its lane has no instructions). Each half speaks only for itself — a link never re-sends the lanes, a move never re-sends the instructions:
    - `Kanban: this session is on card <id>. Always keep its lane matching your actual status with kanban update (no cardId).` (38 tokens) — the card half changed; nothing else follows. The second sentence is the one standing instruction: a session that never hears it lets its card sit in a stale lane while the board shows work that finished hours ago. A same-lane `update` is a no-op (no write, no revision bump), so repeating it is free.
    - `Kanban: this session is no longer on a Kanban card.` (13 tokens) — once, after a browser unlink.
    - `Kanban lanes in board order: lane-backlog,lane-todo,…` (25 tokens) — the lane half changed, or the session has never heard it. Bounded by `KANBAN_NOTICE_LANE_LIMIT` (24) with a `+N more (kanban read lists them)` tail.
  - **A fresh composer's card pick is written before that first run** (`attachNewSessionCard()` from the prompt route, see the store section), so the very first notice of a board-attached session already names the card — the model is never told "no card" for a session that has one.
  - **A card move or rename is not a state transition, and neither is a lane rename**: the ids did not change, so nothing is sent — the model reads the current lane and title from its own `kanban read`/`update` result. That is deliberate: those events fire on every drag, and a per-drag announcement is the cost this feature is removing.
  - **Lane instructions are the exception that fires on every lane transition** (`Kanban lane instructions for Implement (lane-implement):\n<text>`): the card's lane changed into an instructed lane, or the lane's instructions were edited under the card. The header carries the lane's **current name plus its stable id** — the id is the handle `kanban update` takes, the name is what a human recognizes, so a renamed default lane (id `lane-deploy`, now "Review") reads right in the transcript; a rename alone never re-injects (the signature is id + text hash). Never per turn — the `laneId#hash` signature is compared like the other halves, so entry and edit each inject exactly once, and leaving an instructed lane says one dismiss line (`Kanban: the lane instructions given earlier no longer apply.`, `laneInstrDropped`; an unlink needs no dismiss: its card line is the dismissal). The block is bounded at `KANBAN_LANE_INSTRUCTIONS_MAX` (2000) code points with a `…[truncated]` marker — the route's write cap is the same number — so a lane cannot blow the context (~500 tokens once per entry, against the notice's ~40). The instructions never join the lanes line (ids only). The trigger is the board itself, read at every run: the agent's own `kanban update` move and a browser drag/advance are the same trigger, and a session that starts with its card already in an instructed lane counts as an entry (first run has no prior state). The half is project data with the trust level of cards: injected as text, never executed, never fetched from the network.
  - Dedupe keeps the halves apart. This process's memory is the first source (also updated after a successful `create`/`update` **of its own card**, so the tool result the model just read is not echoed next run; with no earlier notice there is no lane half to keep, so the memory is left alone and the next run announces lanes and card together; only the card half is written — the stale `laneInstr` half means the next run injects the new lane's instructions, which is wanted). Falling back to the last notice entry **in the current context**, so a reload, reopen or resubscribe stays silent (a card the session's own tool created in an earlier process re-announces once: that memory never left the process, and one line beats a blind run). A notice persisted before lane instructions existed has no third half and reads as `none`.
  - **Compaction is handled, and must stay handled.** The fallback reads `buildContextEntries()` — the leaf's compaction-aware context, what the model actually sees — not the append-only file, and this process's memory counts only while the context it was recorded in still has at least that many entries (`seenAt`). A compaction that summarized the notice away therefore repeats it once (a branch switch that shrank the context does the same): a blind model would let a card sit in a stale lane for the rest of a long session. Once repeated, the new memory covers the smaller context, so it is one repeat per compaction, not per turn. Covered by the compaction case in `lib/kanban-extension.integration.test.mjs`; removing the `seenAt` guard fails it.
  - Total cost: 25 tokens for the first run of a project session, then 13–62 tokens per real change and per compaction — plus the lane-instructions block (bounded at ~500 tokens) once per lane entry, edit and compaction — and nothing per turn.
  - The read behind it is `readBoard({ create: false })` on the session's cwd, and any failure (a removed worktree, a refused folder, another build's schema) returns `undefined`: the notice may never turn into a failed prompt. The handler is wrapped in try/catch for the same reason. Coverage: `lib/kanban-extension.integration.test.mjs` drives a real SDK session through first run → link → own update → external move → lane rename → lane added → unlink and pins one notice per real change, `display: false` and the persisted state; a second test drives the lane-instructions half (entry → silence → edit → leave/re-enter → own-update moves → one compaction repeat). `lib/kanban-extension.test.mjs` pins the lines, the halves' signatures, the truncation marker and the lanes cap.
- **Do not add a "return every card" read back.** A caller that wants a card's body asks for that one card (`read { cardId }`); a caller that wants to find cards searches. Anything that reintroduces a whole-board payload (`cards` on the overview, full descriptions in search rows) undoes the point of this split. Coverage: `lib/kanban-tool-domain.test.mjs` pins the shapes and a 300-card/4000-character board whose overview stays under 2 KB.
- `cardId` accepts the id or the key (`PIW-42`) everywhere, and `read {}` returns `cardPrefix` so the model can build a key without reading a card. Numbers are allocated by `nextCardNumber()` in the same reducer the browser uses.
- `create { title, description?, laneId? }` defaults to an independent, **sessionless Backlog** task. An explicit work lane creates and attaches the task to the executing session only when it owns no other card. Create is **not idempotent**: after an uncertain result, read before retrying. To delegate, create a Backlog card and carry its `cardId` in the existing `Agent` prompt; no dispatch API, run launch or continuation is added here.
- `update { cardId?, title?, description?, laneId? }` resolves an omitted ID to the executing session's linked card **under the store lock**. Omitted fields stay unchanged; `description: ""` clears it. Text is trimmed as in the existing board reducers. Blank titles/IDs, an empty patch, unknown fields (including fields belonging to another action), and unknown IDs are errors. IDs come from `read`, not hardcoded default lane names.
- `comment { cardId?, body }` appends one note to a card's thread: `cardId` omitted is the executing session's linked card, an unlinked card is allowed (the same rule text edits follow), another session's linked card is refused, and the body is capped at `KANBAN_COMMENT_MAX`. The answer is `{ ok, action: "comment", comment, card, lane, nextLaneId, currentCardId, revision }`. Its write shares the board's lock and transaction and bumps the revision; it changes no card row, so **nothing is announced** (a comment is not a state transition). Read-only is checked inside `execute` for it exactly as for `create`/`update`.
- An explicit work-lane update on a free card claims, patches and moves it atomically. Foreign-linked cards cannot be edited, even text-only; an actor with another card cannot claim a second. Text-only edits of unlinked Backlog cards stay sessionless. Linked cards cannot enter Backlog. A same-lane update never reorders; a genuine no-op preserves timestamps, file bytes and revision. The next lane follows the board's current configurable order, not a relative advance command.
- Mutation results are `{ ok, action, card, lane, nextLaneId, currentCardId, revision }`; `nextLaneId` is null at the last lane, and `lane` is the full lane, which may carry its model-facing `instructions` (the all-lanes projections never do). `content` contains the same readable JSON that `structuredContent` exposes under `outputSchema`, and `details` keeps it for transcript display. Pi 1.2 retains structured content in execution events and nested results, not persisted tool-result messages; those keep content/details. Failures use `isError: true`, actionable text and `{ ok: false, code, error }`. Store failure codes survive; validation adds `invalid-request`, the read-only policy adds `read-only`, and cancellation is a `refused` result.
- Read-only is checked **inside execute**, so a nested `ctx.executeTool()` call cannot bypass it. The default scans the normal session's latest persisted tool selection on each mutation, never a captured startup selection. A child callback is likewise evaluated per mutation, using the current `ExtensionContext`; `read` and `search` stay allowed (the gate names `create`/`update` explicitly, so a new read-only action is not blocked by default).
- `lib/kanban-tool-domain.ts` is the dedicated pure guarded reducer/projection layer (`kanbanToolOverview`, `kanbanToolRead`, `kanbanToolSearch`, `kanbanCardExcerpt`, `kanbanCardSummary`); `lib/kanban-tool-schema.ts` holds schemas (one output branch per read shape) and `lib/kanban-tool-limits.ts` the budgets both read. `executeKanbanToolRequest()` in the store validates the actor's saved session against the cwd's resolved project (worktrees share it), then uses the same queue and file lock as browser edits. It never calls link reducers that silently drop other links. Agent calls do not prune unrelated/dead owners: discovery and retry-safe no-ops must not rewrite other cards. Agent refusals do not materialize a missing board or retire migration sources. Cancellation is checked before entering the write queue, after acquiring the lock, and after awaited validation/editing immediately before writing. The SQLite schema is unchanged.

## Card comments (the handoff trail)
- A card keeps a thread in `card_comments`: **who** wrote it (`author` `user` | `agent`, plus the writing session's id and a snapshot of its name), **what** (`body`, Markdown, capped at `KANBAN_COMMENT_MAX` = 4000 code points by the route and the agent tool — the card's description is where long text goes) and **when** (`created_at`). A thread is append-only for the agent (it has no delete) and the user may remove their notes.
- **A thread is never part of the board payload.** `GET /api/kanban` and its 2.5 s poll are unchanged, so comments cost nothing until a card is open: the detail tab reads `GET /api/kanban/comments?cwd=&cardId=` (newest 100, oldest first), and refetches when the board **revision** moves — which is how a note the agent writes reaches an open tab, and how one tab's note reaches another.
- **Writes ride the board's own lock, queue and revision**: `POST /api/kanban` with `add-comment { cardId, body }` or `delete-comment { commentId }`. The store's `editBoard` runs the board edit and the comment write in **one transaction** and, when the board itself did not change, still bumps `meta.revision` (`bumpRevision`) — that bump is the only sync signal a thread has. A comment on a card that is not on the board is a `refused`; deleting an id that is already gone is a **success** (two tabs racing to delete the same note is not an error). Neither write prunes dead session links.
- Deleting a card takes its thread with it (the orphan prune in `writeBoardRows`); deleting a lane relocates cards and keeps their threads (the card ids do not change).
- **The agent writes with `kanban comment { cardId?, body }`** (see the tool section): an omitted `cardId` is the session's own linked card, and an **unlinked** card is fair game — the same rule a text edit already follows — while another session's linked card is refused. A note is the session's journal: the handoff, the decision, what is left. Nothing is announced: a comment is not a card state transition, so the `before_agent_start` notice stays silent for it.
- `read { cardId }` carries the thread: the newest `KANBAN_COMMENT_READ_LIMIT` (10) entries, each body bounded at `KANBAN_COMMENT_BUDGET` (800) code points with a `…[truncated]` marker, plus `commentCount` (the whole thread). The overview and `search` still send **no** comments, and `read {}` does not either — a model that wants the trail asks for that one card.

## Card activity (the derivation trail)
- Every card keeps an append-only trail in `card_activity`: **what the board did to it** — `created`, `moved` (with both lane names), `title`, `description`, `linked`, `unlinked`, and `lane-deleted`. It is the answer to "what happened to this card?", the question a comment thread only answers when someone wrote a note. A person's note and a derived motion are one story and are rendered in one list (`Activity` in the detail tab), but they are stored, read and capped apart.
- **No caller posts an event.** `editBoard` (`lib/kanban-store.ts`) hands the before and after boards to the pure `deriveKanbanActivity` (`lib/kanban-activity.ts`) inside the same lock and transaction as the board write, so a drag, a menu move, the demo advance and the agent's `kanban update` all record the same thing by construction — the client has no write path for it, and a hand-written board edit cannot produce a lying row. A write that changed nothing records nothing: the reducers return the **same board object**, so `before === after` is the no-op test. The first write on a project with no board file passes the events it derived to `initializeBoard`, so a brand-new board's first card is not the one card with no history.
- **What is not an event**: a position-only reorder inside a lane (one row per drag with nothing to learn), a lane rename (the card did not move), a comment (an authored entry, not a motion), and anything board-wide (lane added, lane reordered). `delete-lane` is the one structural change with its own kind: it relocates and unlinks the lane's cards, and one `lane-deleted` row per card (from the removed lane's name, to the destination's) reads better than a move plus an unlink the reader has to connect. Deleting a card is not an event either — the card is gone, and its trail with it.
- Attribution: `actor_session_id` / `actor_session_title` are set when an agent tool call wrote the change (`editBoard`'s `activityActor`, supplied by `executeKanbanToolRequest` and `attachNewSessionCard`) and null for a person in the browser. The UI shows `via <session>` only when there is an actor.
- **Retention is bounded per card** (`KANBAN_ACTIVITY_KEEP` = 200, pruned in the insert's transaction): a board file lives forever, a single card's history does not need to.
- **The trail is never part of the board payload and never part of the run notice.** `GET /api/kanban` and its 2.5 s poll are unchanged, and a comment or activity write only moves the revision. `GET /api/kanban/activity?cwd=&cardId=[&before=<activity id>]` → `{ cardId, activity, total, revision }`, oldest first, the newest `KANBAN_ACTIVITY_PAGE_LIMIT` (50) rows or the page before the cursor. The cursor is an **activity id, never an offset** (a concurrent write must not shift a page; an unknown cursor reads the newest page instead of failing), and `readCardActivity` orders by `rowid`, i.e. insertion order. Like the comments route it never creates and never prunes (a board with none answers empty at revision 0), and it takes the same request gate.
- `read { cardId }` carries the newest `KANBAN_ACTIVITY_READ_LIMIT` (5) rows as one-line projections (`{ kind, at, from?, to?, actor? }`) plus `activityTotal`; the overview and `search` carry none. That is the point of the feature for a session: it sees what its predecessor did without reading a transcript or a comment the predecessor may not have written.

## Store, lock and revision (`lib/kanban-store.ts`)
- Every write is read → reducer → write under an in-process queue (`serializeByKey`, one chain per board file) plus a `proper-lockfile` lock, as `lib/session-ui-state.ts` does. The lock is held across the whole open-edit-write (`editBoard`), so a second writer waits rather than interleaving. The lock waits through 10 exponential retries (25 ms doubling to a 500 ms cap, a ≈ 3.3 s budget) and answers 423 when that budget runs out; a lock held for more than 10 s is treated as stale and taken over, so a crashed server never pins a board.
- SQLite is opened with a 5 s busy timeout (`DB_TIMEOUT_MS`). If a foreign connection still holds the write lock, the store answers `locked` (423) rather than throwing: `SQLITE_BUSY`/`SQLITE_LOCKED` map to `locked` in `toFailure()`, never to `internal`.
- **`attachNewSessionCard()` is the one write that trusts its caller.** The prompt route calls it for the session it is about to prompt, before pi has written that session's file (it lands with the first message), so it skips `validateSession` — and it must not prune, or `pruneDeadLinks` would unlink the session it just attached. Its rules live in `attachSessionCard()` (`lib/kanban-shared.ts`): a backlog card advances one lane first, a work-lane card is linked as it is, `{ laneId }` creates the session's card there (an unknown lane falls back to the first work lane), another session's card and an unknown card are refused, and a session's own card is reused so a retried prompt is not a second card. An attached id stays in a 15 s grace set, so a pruning read landing in that gap (`aliveSessions()`) cannot read the fresh link as dead.
- `set-card-prefix` is its own branch of `applyMutation` (like the comment writes): it normalizes the value, asks `takenCardPrefixes()` whether another board holds it, and only then runs the reducer. Everything else resolves card references first (`resolveKanbanActionRefs`), so one route serves ids and keys alike.
- Store functions return typed results (`{ ok, board, revision } | { ok: false, code, error }`) — nothing throws at the route.
- A mutation that changes nothing writes nothing; the revision does not move, so the poll sees no change.
- A refused **browser** mutation can materialize a missing board, so the next read sees a real revision. Agent-tool refusals do not initialize/repair/import a board or retire migration sources.

## Pruning (dead sessions)
- On a creating board read and inside every browser mutation (same lock), a card whose `sessionId` no longer has a session file is unlinked (noncreating reads and agent-tool calls do not prune): it keeps its lane and its snapshot `sessionTitle`. A read writes only when something was actually dead. Existence is the cached session path re-verified with `existsSync`; a stale path cache is invalidated and re-resolved (a dead session costs one directory scan, once — the link is gone afterwards). **A link is never unlinked for any other reason**: not because the session's cwd no longer resolves to the board's project (a leftover worktree directory whose git entry is gone, a removed one, a transient git failure) and not because the session was moved to another project. Pruning reads the file and its header (`sessionCwdOf`), never the project comparison `validateSession` keeps for linking — losing a link costs the user the only path back to the transcript, a stale link costs one click on Unlink.
- A session belongs to a board when its header `cwd` equals the board folder **or** `resolveProject(header.cwd).projectRoot` does. The client keys boards by `session.projectRoot ?? session.cwd`, so worktree sessions count against the project root.
- A session's existence for `link-session` / `create-card-for-session` / `add-card` is checked in the store (`applyMutation`) before any lock or mkdir.

## Board rules (`lib/kanban-shared.ts`)
- Reducers return a new board, the same object for "nothing changed", and `null` for "refused"; callers pass `now`.
- **A card's order inside its lane is its position in `board.cards`** — there is no position field (so no schema change, no migration). `cardsOfLane` filters in that order; `placeCard` is the one insertion helper, and `sameLaneOrder` decides whether a move wrote anything. A card anchored on itself (`beforeCardId === cardId`) is a no-op, not the lane's end: `placeCard` looks for the anchor among the OTHER cards and would miss it. A move carries `beforeCardId`, never an index: pending writes are replayed by folding actions over the server board, and an index would point at a different card under a concurrent edit.
- The first lane is the fixed backlog (`lane-backlog`, `fixed: true`): its cards carry a title and a description only, never a session. It cannot be renamed, moved or deleted, no lane swaps past it, and a lane drag never offers it as a source or target (`reorderLane` clamps every drop to index 1 and later, and the drag hook refuses to pick the first lane up), `ConfigLaneRow` draws it with a padlock and no grip, the card form has no session picker there, and the composer's lane menu disables it ("The backlog never takes a session").
- The backlog boundary is the one rule a move obeys, and it is the same one the views gate drop targets with (`canRestInLane`): a sessionless card may not enter a work lane, **a card with a session may not enter the backlog** (`null`), and a backlog card still advances one lane (`advanceCard` is not guarded that way). A move that stays in the card's own lane skips those entry rules — the card is already there, only its position changes — so a hand-edited board can always be tidied.
- `moveCardToLane(board, cardId, laneId, now, beforeCardId)`: into `laneId`, immediately before `beforeCardId` when that card is in the lane, last in the lane otherwise (no anchor — the default — or an anchor another tab moved away). Same lane with the same result returns the SAME board, so a drop where the card already was writes nothing (the revision does not move). `advanceCard` places the card last in the next lane.
- **`deleteLane` relocates the lane's cards to the backlog** — unlinked, with the snapshot title kept (the backlog holds no session). The old mock refused to delete a lane with cards; the lane config dialog still disables Remove while a lane holds cards (`kanban.configureRemoveBlocked`), so the UI never asks for the relocation, but the API does it.
- **Unlinking keeps `sessionTitle`** (only `sessionId` clears), including the old card when linking a session that was on another card.
- One session, one card: `linkCard` / `addCard` drop the link off any other card carrying the session; `createCardForSession` reuses the existing card (only the title refreshes) and otherwise adds one in the composer's lane, falling back to the first work lane.
- Lanes after the backlog are user-configurable: add, rename (Enter or blur saves), edit their text (`edit-lane { laneId, description?, instructions? }`: the UI description and/or the model-facing instructions; at least one field required, `instructions` capped at `KANBAN_LANE_INSTRUCTIONS_MAX` = 2000 characters by the route, an empty string clears, the fixed backlog refused — deliberately its own action, not an overload of `rename-lane`), reorder, delete (`LaneConfig` + `ConfigLaneRow` in `components/KanbanBoard.tsx`). Reordering is `move-lane` (±1, the rows' up/down buttons) or `reorder-lane { laneId, toIndex }` — a direct move for a drag drop, clamped to `1..lanes.length - 1`, `null` for the fixed backlog or an unknown lane, the same board for a no-op drop on the lane's own position. **A rename keeps the id** — only the six default lanes carry readable ids (`lane-deploy` may be named "Review"), user-created lanes get uuids — and delete-plus-recreate is NOT a way to "fix" an id: `delete-lane` relocates the lane's cards to the backlog, unlinks their sessions and drops the instructions.
- The user moves a card with `move-card` — a drag, the card menu's Move up / Move down, or its "Move to {lane}" entries — and the board's own order is the result: the drop gap is `beforeCardId`, one step inside the lane is the same action with the card's own lane. Advancement is a demo action standing in for the model's decision: "Demo: advance to {lane}" (`kanban.menuAdvance`) on the card menu and the strip menu calls `advance-card`, one lane right, last in it. Linking a session does **not** move the card, and neither does unlinking.
- Each project directory has its own board (`kanbanContextDir`: the session's `projectRoot ?? cwd`, for a fresh composer its context project's root). Board lookup/open includes all sessions of that project, including subagents in worktrees (`lib/kanban-sessions.ts`). A child-linked card opens its read-only viewer through `handleOpenSubagentTab`, never selecting/reopening the child or starting a run. That viewer takes no input; its notice hands the user over with `handleOpenSubagentParentChat(parentId, childId)`, which selects the parent's chat (leaving a `?board=` view) and opens the agents panel focused on the child's row — interacting means prompting the child in the parent's chat, never from the board. Even when the board belongs to another project, viewing leaves the chat/workspace and board unchanged, so project-switch cleanup cannot drop the viewer. Manual Link and new-card pickers remain top-level-only; an edit form also keeps the card's existing child as a choice, using the saved title if its catalogue row temporarily disappears. Saving only text preserves the session id and its saved title.

## Client cache (`lib/kanban.ts`)
- A module-level `Map` of entries keyed by project root. An entry holds the last `serverBoard`, its `revision`, the `pending` writes and the shown `board` = server board with pending writes folded on top (the `useSessionUiState` pattern). `useKanbanBoard(dir)` returns that board or `null` while loading; `useKanbanBoardStatus(dir)` returns `{ status: "loading" | "ready" | "error", error?, retry() }`. The banner's `retry()` does three things: it re-enqueues the writes the entry kept as `retryable` (the session-missing failures from the section above — re-posted, not dropped), clears the error, and refetches with the entry's normal read kind — a creating read only while a board-view (creating) watcher holds the board, so a board whose initial creating read failed is created now; a strip-only board refetches non-creating, as its quiet resyncs do).
- Mutation functions keep the mock's names and **synchronous** return values (`kanbanAddCard` → `KanbanCard | null`, `kanbanAdvanceCard` → `KanbanLane | null`, the rest `void`). Each runs `applyKanbanAction` from `kanban-shared` first: a `null` refusal never posts and changes nothing; a same-board result does not post either. Otherwise it is applied optimistically and POSTed, writes of one board go out one at a time. On success the server's `{ board, revision }` replaces the cache (and a GET that began before it is discarded via `loadId`); on failure the pending write is dropped (rollback), the status turns `error` and a quiet refetch resyncs. Without a loaded board, mutations are no-ops except `kanbanCreateCardForSession`, which posts blind (the server holds the rules). `kanbanBoardSnapshot(projectDir)` reads the shown board outside a render — the pending attach's consume-time lookup — and `kanbanBoardSnapshotForTests` delegates to it.
- Polling: watching a board (`useKanbanBoard` / `useKanbanBoardStatus`) fetches it on mount, then `GET ?cwd=&revOnly=1` every 2.5 s (the running-sessions cadence in `SessionSidebar`) while the tab is visible — skipped while hidden, one check as soon as it is shown again — and a moved revision refetches the whole board. One in-flight fetch per board; the poll does nothing while a write is pending. A board with no watcher is not polled.
- **Activity has its own cache entry per card** (`${projectDir}\0${cardId}`, `useKanbanCardActivity`), read the same way: fetched when the card is first shown, refetched when `useKanbanBoardRevision` moves past the revision the entry holds. A first-page refetch **lays the newest page in front of the older pages this tab already loaded** (dedupe by id), so a reader who scrolled back keeps their place when the agent moves the card; `loadOlder()` asks for the page before the oldest row it shows, and `hasMore` is `activity.length < total`. Nothing is optimistic: the server derives the rows, the client only reads them.
- **Comments have their own cache entry per card** (`${projectDir}\0${cardId}`): `useKanbanCardComments(projectDir, cardId)` reads it and refetches when `useKanbanBoardRevision(projectDir)` moves, past the revision the entry already holds. `kanbanAddCardComment` / `kanbanDeleteCardComment` POST through the board route, adopt the answered board (so the revision moves for every watcher) and then reload that one thread; a failed write marks the thread `error` and reads nothing. Nothing is applied optimistically: a note is a row the server stamps.
- `useKanbanSessionIndex()` derives `Map<sessionId, KanbanSessionInfo>` from the boards **loaded in this tab** (the current project's, plus any other the user opened); the sidebar's tracked marker therefore shows for the watched project's sessions, not every project's.

## Surfaces
- **Chat-top lane strip** (`components/KanbanLaneStrip.tsx`, `ChatWindow`'s `kanbanStrip` prop, first child of `.chat-content`): the project's lanes left to right as pills, only the card's lane highlighted (a dot on it while the session runs), the card title at the left. It renders nothing until the board has loaded (a strip flash is worse than momentary absence) and has no status UI. The menu offers View board, the Demo advance (same gating as the card menu: only while a next lane exists, dimmed) and Unlink; an untracked session gets "New card in {lane}" plus "Attach to" the board's sessionless cards, newest first and uncapped (the menu's own filter, shown past six entries, finds the rest). The pill states: only the current lane takes the accent tint and the running dot; past lanes a plain hover tone, the rest 55% opacity; the pending pill is dashed. The label at the left is the card's title when tracked, "Not on board" for an untracked session, and the pending text for a fresh composer; a fresh composer with no pending lane renders no strip at all (`isNewSession && !card && !showPending` → null). A fresh composer shows its pending choice as a dashed pill on the lane it will touch — a new card's lane, or the attached card's current lane (**a backlog card's next lane**: the attach advances it one lane first, so the pill must not mark the fixed lane the card is leaving; nothing is highlighted when there is no lane to advance into, because the attach would be refused) — labeled "New session — starts in {lane}" or "New session — starts on card {title}"; the pill highlights only while the lane resolves (a card deleted on another device leaves the label alone).
- **New-session composer** (`components/NewSessionContextBar.tsx`): the "Track on board" choice (the `board` prop, `data-kanban-board-choice` menu) is three-way — Off, "New card in" a lane (backlog disabled, tooltip says why), or "Attach to card" one of the board's sessionless cards — newest first (`sessionlessCardsByRecency`), uncapped, each row tagged with its lane; past six cards a filter field narrows the list by title (the card menu's filter pattern, `kanban.composerCardFilter`), with a disabled "no match" line when the filter empties it and a disabled "no cards" line when the board has none. The pick (`KanbanNewSessionPick`, `lib/kanban-types.ts`) is AppShell state (`newSessionKanbanPending`, pinned to `composerBoardDir` by `handleNewSessionKanbanPick`), owned by the parent, not the bar. It is per composer: the reset effect runs on every `composerBoardDir` change and keeps a choice only for the same board (a worktree move keeps it — the board belongs to the project root), **comparing boards, not path spellings**. A worktree cwd is its own "project root" until the sidebar resolves it (`contextForCwd` falls back to `{ root: cwd }`), so a composer mounted at `?cwd=<worktree>` goes worktree path → project root a beat later; the pick is **re-pinned** to the resolved dir in that step, and only a dir resolving through the same context to a *different* project root (or no composer at all) parks the choice. The raw string comparison here dropped a card picked in that first beat — the session then started untracked, intermittently, because the pick (not the user) was blamed for the move (`components/AppShell.kanban-composer-pick.test.mjs` runs this effect and fails on the string comparison). `handleSessionCreated` clears the pending pick (state + ref) when the session is created. **The pick rides the session's first prompt** (`POST /api/agent/[id]` carries `kanban: { cardId } | { laneId }` from `useAgentSession`): the route applies it **before** `session.send`, so the run's own board notice already names the card. pi runs `before_agent_start` while handling the prompt, so a link posted afterwards — what the browser did once it learned the session id — always reached the model one turn late; and a pick the client could not validate (`kanbanBoardSnapshot` miss, an unloaded board in `mutate()`) was dropped with no POST, no toast and no retry. The route answers with `kanban: { board, revision } | { error, code }`: the client adopts a board it already wrote (`kanbanAdoptServerBoard`) instead of posting the link a second time, and keeps the old client path only as the fallback for an answer without a `kanban` field. A refusal never fails the prompt — the session starts and the strip says "Not on board". Its lane and card lists are empty until the board loads (`contextBoard`).
- **The card detail tab** (`components/KanbanCardDetail.tsx`, right-panel tab, `Tab.kind: "card"`, id `card:<cardId>`): a card has exactly one destination — clicking it anywhere on the board (or the card menu's Edit) opens or focuses that tab and opens the panel, and its tab label follows the card's title. The tab is page memory like a subagent tab: no persistence, dropped when the project changes (`changeFileWorkspace`), closed by its own ×, and closing it touches neither the board nor the card. It carries the lane and the session as **themed popups, not native `<select>`s**: a chip opens the board's own `CardMenu` (portaled, outside-close, Escape, phone bottom sheet), because a native option list is painted by the browser outside the control's box — it keeps the platform's light surface under a dark theme's ink (Chromium ignores author option backgrounds; `app/globals.css` still names `select option` colors for the settings selects Firefox and Safari honor). The lane entries gate through `canRestInLane`, a refused one disabled with the rule as its hover text ("The backlog never takes a session" / "A card without a session can only rest in Backlog"), and the session entries are the project's sessions plus the way back to none (absent while nothing is linked, and a project with no sessions says so instead of opening empty). An unlinked card keeps its snapshot `sessionTitle`, so the picker names a session only while `sessionId` is set — otherwise it reads "No session yet", the session (chip → open the chat, select → link/unlink, "Start session" for an unlinked card — **a backlog card's included**: the backlog takes no session, so the attach advances it one lane first, which is why the row reads **Start session → Todo** (a tinted accent pill, the lane as its consequence, the rule in its tooltip; no chip and no sentence, the button is the whole control) and why no start button is offered when the board has no work lane to move it into (then the plain rule chip returns); the row's `Updated …` sits right-aligned; the composer path is the card menu's, `handleKanbanStartSession`, given the card tab's own project — a card tab survives another project's board being on screen), the title, the Markdown description as **Write / Preview** (Ctrl+Enter or Save, `MarkdownBody` for the preview, `projectDir` as the render's cwd, and `keepLineBreaks` — a note is typed, not typeset, and agents write a card one line per point, so the preview renders every line ending as a line; the same holds for each comment body) and the **Activity** journal: one oldest-first list of the card's comments (authored entries, the existing `CommentEntry` cards) and its derived activity rows (22 px lines on a 1 px rail, accent glyph on a move), with the comment composer pinned under it (Ctrl+Enter, delete on your own notes). Events are the frame, comments are the content: an event never gets a background, border or box, and a run of same-actor events inside 10 minutes shows one time label on its last row. `Load older` pages the history; a card whose history predates the feature shows its notes and no rows. There is deliberately **no Escape handling**: the window's Esc stops a run and the board owns its own, so a detail tab must not steal it.
- **A card is created in that same view.** A lane's `+` opens the tab in draft mode (`card:draft:<n>`, `kanban.detailDraftTitle` as its label): lane and session pickers, title, description, the title field takes the caret as soon as the editor is on screen (a `titleAutoFocused` ref holds it to once per tab, and the effect waits for the board's first render, since the tab shows `kanban.loadingBoard` until then), so a new card needs no click first; then **Add card**, which writes with a client-chosen id (`kanbanAddCard`) and retargets this tab to `card:<newId>` (`handleKanbanCardCreated`) instead of opening a second one. The inline `CardForm` remains only as the fallback for a board rendered without the shell's handlers (`onOpenCard` / `onNewCard` absent: node tests), and the card menu keeps its Edit entry — which now opens this tab rather than the inline form.
- **Sidebar** (`components/SessionTree.tsx`, via `SessionSidebar`'s `kanban` prop): a tracked session row shows the small board glyph (`session-tree-kanban`, "On board · {lane}") for the family root id from `useKanbanSessionIndex()`, which AppShell calls and passes down (the tree only reads it), only family roots have sidebar rows, so a child's independent card never replaces its parent's lane marker. - **The board itself** (`components/KanbanBoard.tsx`): lane columns, a card form and the card menu (`CardMenu`), the link picker (`SessionPicker`), and the lane config dialog over the columns. A card is also draggable to another lane: `hooks/useKanbanCardDrag.ts` runs the same pointer state machine as the sidebar's group drag (mouse arms after 4 px, touch/pen after a 350 ms held press with 8 px slop, second-finger and Escape cancel, auto-scroll at the edges), but hit-tests the lanes by rect (`data-kanban-lane` / `data-kanban-lane-cards`) instead of drop targets, auto-scrolls the row horizontally plus the hovered lane's card list vertically, and floats a ghost over the board while the source card dims; releasing posts `move-card`. **The drop lands in a gap, not just at the lane's end**: `insertionBefore` reads the target lane's card rects and takes the first card whose vertical midpoint is below the pointer, so a release puts the card between any two cards, above the first one, or at the end. The view carries that gap as `beforeCardId` and the lane paints a 2 px line there (`DropLine`); the dragged card stays in the DOM during its drag (no reflow, and dropping it where it already was is the reducer's no-op) but `insertionBefore` skips it, so a drop above the dragged card's own top half anchors on its neighbour — dragging the first card up leaves it first instead of sending it to the lane's end. The source lane is a legal target (a reorder) and is never marked undroppable. A LANE is draggable the same way (`hooks/useKanbanLaneDrag.ts`, the same pointer state machine; mouse arms after 5 px, touch/pen after a 350 ms held press with 8 px slop, second-finger and Escape cancel, auto-scroll at the scroll box's edges): on the board a column's header is the handle (axis `x`, the buttons inside it excepted) and in the config dialog a row's six-dot grip is (axis `y`, `allowTouch`, so a swipe still scrolls); the drop index comes from the lanes' rects — the gap before the first lane whose midpoint the pointer has not passed, converted for the row the drag removed, never index 0 — an accent line marks it (a vertical `ColumnDropLine` between the board's columns, a horizontal `LaneDropLine` between the dialog's rows, both rendered in the row list between the dragged lane's new and old neighbours), a `LaneDragGhost` chip floats over the pointer while the source column/row dims, and a release posts `reorder-lane` (a release on the lane's own position posts nothing). From pick-up, every lane the move-card rules refuse for the card in flight shows itself undroppable — dashed red border, red wash, `no-drop` cursor, and a one-line reason in the lane header (the source lane excepted) — and a release on one bounces back with no write. In the phone's one-lane view the same held press opens the card menu instead (the menu's outside-close ignores that press's synthetic mousedown for a short window), so the menu is the phone's — and the keyboard's — move path. The card menu's entries are gated by link state: a linked card gets Open session (disabled with "That session is no longer available" when the session is gone) and Unlink; an unlinked one gets Start session (always enabled; `onStartSession` hands the card to AppShell's `handleKanbanStartSession`, which opens the fresh composer for the board's project with the card's title and description as the starting draft — parked under the cwd's draft key so `handleNewSession` picks it up — pins the pending attach choice and switches to the chat view; the session is linked when it is created, nothing is written before) and Link (disabled for a backlog card or a project with no sessions, opening the picker otherwise); Edit is always there, then Move up / Move down (`kanban.menuMoveUp` / `kanban.menuMoveDown`: one step inside the lane, disabled at its ends — the keyboard and touch peer of a reorder), then "Move to {lane}" for every other lane (disabled where the rules refuse it, with the reason as the hover text), then the dimmed "Demo: advance" (only while a next lane exists); Delete is last, marked danger. **The card menu has no filter field**: a card menu is a handful of rows (link state, Edit, Move up / down, one "Move to" per other lane, the demo advance, Delete), the field took an extra tap on a phone and the keyboard it raised covered the very rows it narrowed, and its gate (`visible.length > 6`) unmounted the input — caret and all — as soon as a query left six rows, so a query could be neither finished nor cleared. Focus lands on the first action instead (arrows and Enter walk from there) and Escape closes on the first press. `SessionPicker` keeps its own field: it lists every session of the project, uncapped. **Both survive the soft keyboard that field may raise**: a `window.resize` whose width did not change is treated as the keyboard's, not as a real resize — `app/layout.tsx` sets `interactiveWidget: "resizes-content"`, so focusing a field resizes the layout viewport and the board's `resize` listener used to close the menu one frame after it opened. `lib/soft-keyboard.ts` decides (`softKeyboardBand`, `isSoftKeyboardResize`: a pinch zoom shrinks both viewports together, so it reads as no keyboard), `hooks/useFloatingPlacement.ts` re-places the popup into the **visual** viewport once per frame plus a settle pass (WebKit reports the shrunken viewport only after its animation, bugs.webkit.org 265578) and clamps its height to it, and a real resize (the phone turned) still closes both. **Never key an open popup's fate off a bare `resize` event on a phone.** The config dialog's rows: rename saves on Enter (via blur) or blur; each work lane also holds a **textarea for its model-facing instructions** (`kanban.configureInstructionsPlaceholder` says what it is and that Ctrl+Enter saves — plain Enter keeps the newline; `maxLength` is the same `KANBAN_LANE_INSTRUCTIONS_MAX` the route enforces; blur saves through `kanbanEditLane` → `edit-lane`), which the fixed backlog never shows (its cards carry no session, so nothing would inject); up/down are barred for the fixed backlog and at the edges, and Remove is enabled only for a lane with no cards (`kanban.configureRemoveBlocked`). While the board loads the lanes' area holds a slim placeholder (`kanban.loadingBoard`) inside the same frame (`BoardShell`), so the columns arrive without a layout jump; a failed load or write shows a one-line banner with Retry (`kanban.loadFailed` / `kanban.retry`, `BoardNotice`) above the lanes (the rolled-back board stays visible). The top-bar Chat/Board toggle (`renderBoardViewToggle` in `AppShell`) switches `centerView` (the Chat button forces `chat`, picking any session in the sidebar does too — "the user wants its chat, not whatever the center shows"); it hides when no chat context exists but stays up while the board view is on, so the way back always shows. `AppShell` keeps two watchers: `contextBoard` — the strip's project (the selected session's `projectRoot ?? cwd`, or the fresh composer's context project) — is watched whenever that context exists (the strip, the sidebar's board highlight and the composer's lane list all read it), while `viewBoard` is watched only while `centerView === "board"`. When both name the same project (the common case) they share one refcounted entry, so the current project keeps polling in the chat view; another project's board polls only while it is on screen. Switching back from chat re-acquires `viewBoard`, which checks the revision immediately (acquire's cached-board path) rather than waiting for the next tick. A move (drag, Move to, Move up / Move down or demo advance) rings the moved card for 1.6 s, and arriving with a highlighted card opens its lane in the mobile one-lane-at-a-time view.
- **The link picker** (`SessionPicker` in the same file): a portal `listbox` anchored to its trigger (clamped 8 px from the edges, flips above when the bottom edge is close). ## Client-side card filter
- The board header always shows **Filter cards** before Configure. `components/KanbanSearch.tsx` keeps the field and its theme-token CSS together; a **board-container** query at 620px puts it on a full-width second row even when desktop side panels, not the viewport, narrow the board. Mobile/coarse-pointer text is visually **14px**: the input retains a 16px computed font for Safari's focus-zoom threshold, scaled by 0.875 inside a clipped flex slot. Inverse width/height keep its full tap area; the icon and 32px clear button are not scaled. No autofocus. The loading/error shell retains the header with a disabled field until a board is available.
- `lib/kanban-search.ts` trims and lowercases a **literal substring**, testing title **OR** description (and the card's key, `PIW-42`) independently: never session ids/names, transcripts, lane names, or a title/description concatenation. Every lane and the canonical card order remain. `searchKanbanBoard()` supplies matching cards, original totals, and a separate `renderedCards` list that pins an active edit in place without counting it as a match. The canonical `board` still feeds forms, link/menu lookups, configuration counts and every mutation; hidden cards must still block lane removal.
- The summary is a polite live matched/total count; lane badges and mobile tabs show matched/total while filtering. A board-level no-results message offers Clear; a populated lane with no matches differs from a truly empty lane. Filtering never picks a different mobile lane automatically: an empty filtered lane offers a button to a matching lane. Existing add/edit forms survive query changes until Save/Cancel; their stable keys preserve the unsaved fields.
- Highlights are React text nodes and `<mark>` elements, never HTML or query regexps. Lowercase match offsets map back to original code-point boundaries (notably `İ` expands and shifts UTF-16 offsets); description previews center the first hit within 120 code points, with ellipses only at cut ends and the full match kept even if longer than the budget. Filtered descriptions are **not line-clamped**: a long match or wide CJK text must stay visible. Unfiltered cards keep their old three-line preview.
- A nonblank normalized query disables **card** drag and the card menu's Move up/down, with an explanation specifically about cards. Move to lane still uses the canonical board and its existing rules. Mobile long-press still opens the menu (`mode: "menu"`, enabled even while filtering). **Lane reordering stays available**, both column drag and configuration grips/Move up/down: no lanes are filtered out, so their order is unambiguous. Filtering preserves lane order automatically; it must not block a deliberate lane move. The fixed-backlog rules remain unchanged.
- Raw whitespace remains clearable even though it filters nothing. Clear returns focus to the input. Escape is handled **on that input only**, after dialog/menu capture listeners, and checks `defaultPrevented`, IME `isComposing` and Safari's keyCode 229; never add a document-level search Escape handler that would steal a dialog's close or cancel a card edit.
- Query ownership is AppShell page memory (`boardSearch`, one `{ projectDir, query }`, not a per-project saved history). The board unmounts in chat, but a same-project chat round-trip retains the query. Changing boards or adopting a different chat project clears it; a worktree of the same resolved project does not. Session promotion briefly supplies only `cwd`, with no `projectRoot`: AppShell derives `kanbanContextDir` through the same `contextForCwd(sidebarNewSessionContext, cwd, newSessionMoveRef.current)` fallback as the composer until hydration supplies the root. Comparing the raw worktree cwd would erase the query on root → transient worktree → hydrated root. A cwd outside the known context/move still resolves to its own project and clears normally. Reload starts empty; nothing is written to the URL, localStorage, board cache or backend. An explicit card jump checks `kanbanBoardSnapshot` and clears a hiding query **at the jump**, not on every board render (which would prevent subsequent typing while the arrival highlight lives). Unknown jump targets clear defensively until data arrives. `key={boardProjectDir}` also prevents form/mobile-lane state from leaking between projects.
- Coverage: `lib/kanban-search.test.mjs` (pure matching/projection/excerpts/lifetime), `components/KanbanSearch.test.mjs` (clear/focus/IME), `components/KanbanBoard.search*.test.mjs` (rendered states and hook-shim interactions, including lane reorder availability), `components/AppShell.kanban-search.test.mjs` (actual context/effect code across worktree promotion, hydration and genuine project switches). ## Traps
- **Never store a card's key, and never store the prefix on a card.** `meta.card_prefix` + `cards.number` is the pair; a stored key would go stale on a rename, and a per-card prefix would let one board show two. Same rule for the alias list: aliases resolve, they are never rendered.
- **Never reuse a card number**, and never derive the next one from `max(number)`: an empty-board-with-history (the highest card deleted) would hand the same number out twice. `meta.next_card_number` is the counter. A duplicate `number` breaks `cards_number` and would make one key name two cards.
- **A same-lane no-op must not allocate.** `addCard` is the only allocator, and it runs only on a real insert; anything that bumps `nextCardNumber` elsewhere makes a drag leak numbers.
- **A prefix is a namespace, not a label.** Enforce uniqueness on save and refuse the collision rather than quietly sharing it: two boards reading `PIW-42` make the reference useless everywhere it is written down. The same rule is why a foreign prefix never resolves — a reference must fail loudly, not land on the wrong card.
- **Never announce the card notice unconditionally.** A `before_agent_start` message is appended to the transcript as a `custom_message` entry, one per run, so an unconditional notice grows the context on every turn — the exact waste the read projections just removed. Compare the two state halves (memory → transcript) and return `undefined` when neither changed. And never put card counts, revisions or timestamps in the lanes line, nor fire on a card move: they change on every drag, so the notice would re-send the whole lane list each time a card moves. Also keep `display: false`: without it the chat draws the notice as a message the user never sent.
- **A phone's soft keyboard is a resize event, not a blur.** `app/layout.tsx` sets `interactiveWidget: "resizes-content"`, so a focused field (the card menu's and the link picker's filter) resizes the *layout* viewport for the keyboard's whole animation. Anything that closes an open popup on a bare `window.resize` closes it one frame after it opened — the card menu's "opens then instantly hides" report. Only a resize that changes the **width** is real (`lib/soft-keyboard.ts:isSoftKeyboardResize`; a pinch zoom shrinks both viewports together, so it reads as no keyboard); the popup re-places itself into the visual viewport for the rest (`hooks/useFloatingPlacement.ts`). A field on a coarse pointer also takes no focus by itself (`autoFocus={!coarsePointer}`, 16px so iOS does not auto-zoom), which is what `components/SidebarMenu.tsx` and `components/ModelSelector.tsx` already do for the same reason. Covered by `lib/soft-keyboard.test.mjs` and `e2e/kanban-menu.mjs`.
- `useSyncExternalStore`'s `getServerSnapshot` must return a **stable cached reference** (`null` / the shared `LOADING_VIEW` / `0` here); a fresh object per call triggers "The result of getServerSnapshot should be cached to avoid an infinite loop" and re-renders forever. The status hook's `{ status, error }` view is cached on the entry and only rebuilt when it changes for the same reason.
- `useKanbanSessionIndex()` mutates its module-level `lastIndex` map in place (drops stale keys, rewrites only changed entries) and returns that one map. Unchanged `KanbanSessionInfo` entries keep their identity, so a board change re-renders only the rows whose marker actually moved; a rebuilt map would re-render every session row.
- Board objects are immutable. An identical refetch keeps the old object (`adopt` compares JSON), so memoizing on the board is safe and a poll tick does not re-render.
- Only a creating read (a `GET` without `?create=0`, the board view's) creates the board file for a project that has none (importing the JSON boards first, when one holds a board); the strip and composer watchers send `create=0` and read a missing board as empty (revision 0), so merely selecting a session writes nothing anywhere — not even a connection: a missing board is never opened for writing. Do not add a creating watcher speculatively (e.g. for every sidebar project).
- The "Demo:" prefix on the advance action (`kanban.menuAdvance`) marks the model's decision the user runs on its behalf — one lane right, what the model will post on its own — while the plain "Move to" entries and Move up / Move down are the user's manual `move-card` moves, to any lane and any place the rules allow. Keep that distinction.

- **A card's comments stay off the board payload and off the notice.** The board is fetched whole every time its revision moves and the notice is re-sent on every state change: a thread there would cost tokens on every drag, for notes nobody asked to read. A thread has its own read (`/api/kanban/comments`), its own cache entry, and the one-card read's bounded projection. And **never add a foreign key from `card_comments` to `cards`**: the board write replaces the card rows on every edit, so a cascade would silently delete the user's handoffs.
- **Never post an activity row from the client, and never derive one from anything but the board diff.** The trail's whole value is that it cannot lie: it is written in the board write's transaction from the before/after pair, so a refetch, a retry or a rolled-back optimistic write cannot invent a row. A `before === after` write records nothing — do not "help" by emitting a row per action name.
- **The activity trail stays off the board payload, off the notice and off the overview.** Same arithmetic as comments: the board is fetched whole on every revision bump and the notice is re-sent on every state change, so a trail there costs tokens on every drag for rows nobody asked to read. It has its own read, its own cache entry, the one-card read's bounded projection, and nothing else.
- **A comment write is not a card state transition.** Do not add it to the notice's halves, and do not make the board's optimistic path fold it (`applyKanbanAction` must never see one — a comment is not a board row).

## Not built
- Automatic task dispatch/continuation, scheduling and subtasks. The model can now move its card through `kanban update`; the manual "Demo:" advance remains a separate UI action.
- A push channel for the board (the revision poll is the sync) and undo; several boards per project.
- Filtering or searching a card's activity (the merged journal's filters were designed and deferred: at five rows per card a filter is a setting wearing a button's clothes), a board-wide activity feed, a per-card unread badge, editing or deleting an individual event, retention settings, and backfilling history for cards that predate the feature.
- **Cross-project card references** (`PIWEB-42` quoted inside another project's card) and `@PIWEB-42` mentions in comments: the prefix is unique per machine, so both are addable later, but nothing here resolves across boards today.
- Card keys in the URL, or in worktree/branch names: the key is one click from the clipboard (both chips, and `Copy key` in the menu) and that is the integration.

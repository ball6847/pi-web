# Kanban board (UI design phase)

## What it is
- A per-project task board in the UI design phase (3bbb22b): pure UI, mock data, nothing on the server. `lib/kanban-mock.ts` is the whole state layer — one `KanbanBoard` per project directory in an in-memory `KanbanMockStore` singleton, persisted to `localStorage` under `pi-web:kanban-mock:v1`, with `kanban*()` action functions as the components' only way in. A refresh resumes where the demo left off; a full or blocked storage loses only the persistence, never the view (`commit()` swallows the write error).
- SSR renders the seed and the saved boards follow after hydration: a board never saved in this browser draws `seedBoard()`'s deterministic seed (fixed lane ids, `kb-seed-N` card ids — no clock, no random in the ids), cached per project in the store's `seeds` map so its identity is stable across reads. `boardExists()` is true for any project directory — the mock gives every project a board on demand.
- The board view is an absolute-positioned overlay in the chat area (`AppShell`'s `centerView: "chat" | "board"`; `KanbanBoard` in an `inset: 0` layer beside the chat layer, which stays mounted under `display: none` so the session keeps its state). It is **not** a `TabBar` tab: `TabBar` is the right panel's file/terminal/subagent tabs, and the board never appears there.

## Board rules (`lib/kanban-mock.ts`)
- The first lane is always the fixed backlog (`lane-backlog`, `fixed: true`): its cards carry a title and a description only, never a pi session. It cannot be renamed, moved or deleted (`renameLane` / `moveLane` / `deleteLane` all refuse `lane.fixed`, and no lane may swap past it), `ConfigLaneRow` draws it with a padlock instead of a name field, the card form offers no session picker there (`needsSession = !lane.fixed`), and the composer's lane menu disables it ("The backlog never takes a session").
- The lanes after it are user-configurable: add, rename (inline input, Enter or blur saves), reorder (Move up/Down) and delete, from the board's lane config dialog (`LaneConfig` + `ConfigLaneRow` in `components/KanbanBoard.tsx`). A lane holding cards cannot be deleted — `deleteLane` refuses and its button reads "Remove its {count} cards first" (`kanban.configureRemoveBlocked`).
- The user never moves a card by hand. Advancement is a demo action standing in for the model's decision: "Demo: advance to {lane}" (`kanban.menuAdvance`) on the card menu and the strip menu calls `advanceCard()`, which moves the card one lane right. There is no card drag-and-drop in the mock, and there should not be one later: moving a card is the model's call.
- Cards link to and unlink from sessions at any time (a backlog card and a card whose session left are simply sessionless). One session, one card: `linkCard` drops the link off any other card carrying that session, and `createCardForSession` reuses the existing card instead of adding another. The link picker and "Open session" see the project's top-level sessions only (`boardSessions` filters out `relation.kind === "subagent"`).
- Each project directory has its own board (`kanbanContextDir`: the session's `projectRoot ?? cwd`, for a fresh composer its context project's root). Two seeded sample cards (`seeded: true`, in Todo) auto-link to the project's real pi sessions exactly once: `kanbanSyncSeedLinks` runs from an `AppShell` effect over the project's non-subagent sessions, links at most two sessionless seeded cards, then sets `seedSynced` and never runs again. After a user unlinks a seeded card it stays unlinked — the sync never re-attaches work the user took off the board.

## Surfaces
- **Chat-top lane strip** (`components/KanbanLaneStrip.tsx`, `ChatWindow`'s `kanbanStrip` prop, first child of `.chat-content`): the project's lanes left to right as pills, only the card's lane highlighted (a dot on it while the session runs), the card title at the left. The menu offers View board, the Demo advance and Unlink; an untracked session gets "New card in {lane}" plus "Attach to" up to eight sessionless cards. A fresh composer shows its pending lane as a dashed pill ("New session — starts in {lane}") and no strip at all while tracking is off.
- **New-session composer** (`components/NewSessionContextBar.tsx`): the "Track on board" choice (the `board` prop, `data-kanban-board-choice` menu) picks Off or the lane the session's card starts in. It is per composer and reset when the composer moves to another project (its lanes are a different board's); `handleSessionCreated` in `AppShell` turns the choice into the card (`kanbanCreateCardForSession`) and clears it.
- **Sidebar** (`components/SessionTree.tsx`, via `SessionSidebar`'s `kanban` prop): a tracked session row shows the small board glyph (`session-tree-kanban`, "On board · {lane}") for the family root id from `useKanbanSessionIndex()`; a project group header gets the board icon ("Open {name}'s board") that opens that project's board (`openKanbanBoardView`, which also rings the jumped-to card for 2.4 s).
- **The board itself** (`components/KanbanBoard.tsx`): lane columns, a card form and the card menu (`CardMenu`), the link picker (`SessionPicker`), and the lane config dialog over the columns. The top-bar Chat/Board toggle (`renderBoardViewToggle` in `AppShell`) switches `centerView`; a demo advance rings the moved card for 1.6 s.
- Every label lives in the `kanban.*` keys of `lib/i18n/messages/en.ts`; `kanban.configureNote` is the one paragraph that states the board's rules in the config dialog.

## Traps
- `useSyncExternalStore`'s `getServerSnapshot` must return a **stable cached reference**. `KanbanMockStore` keeps one static `serverSnapshot` object; a fresh object per call triggers "The result of getServerSnapshot should be cached to avoid an infinite loop" and re-renders forever — Next.js dev's overlay will flag it. The same reasoning caches each seed in `seeds`: `board()` must not build a new seed object per read.
- `useKanbanSessionIndex()` mutates its module-level `lastIndex` map in place (drops stale keys, rewrites only changed entries) and returns that one map. Unchanged `KanbanSessionInfo` entries keep their identity, so a board change re-renders only the rows whose marker actually moved; a rebuilt map would re-render every session row.
- The store mutates board objects in place and bumps a `version` on every commit; `useKanbanBoard` uses the snapshot purely as a change signal and returns `s.board(projectDir)` directly. Board identity never changes, so nothing may memoize on it — re-rendering rides on the version bump alone.
- The "Demo:" prefix on advance actions (`kanban.menuAdvance`) marks model-driven moves. Keep it while the demo control stands in for the model: without it the menu reads as a manual move, which the board's rules forbid.

## What a real implementation will need
- An API route plus server persistence in place of the `localStorage` key (the `kanban*()` action functions are the seam: the components already talk to nothing else). Boards would want the same cross-process care as `pi-web-session-state.json` (see [sessions.md](sessions.md), Session sidebar).
- The model advancing cards on the protocol side: the card moves when the model decides the stage is done, replacing the "Demo:" menu entries.
- Cross-browser sync: today's store is one browser, and `useKanbanSessionIndex` reads only boards saved in it.
- A real per-project starting point replacing the mock's seed — `seedBoard()` / `seedCards()` and the `seedSynced` auto-link exist so a demo speaks about real sessions; a real board starts empty and unseeded.
